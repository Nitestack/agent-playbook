agent-playbook: skills, templates and guard hooks for agent repos

A portable kit of plain files. It holds ten workflow skills, templates that bootstrap a repo, three PreToolUse guard hooks and a frozen archive of the decisions behind them. The hooks need bash 4, jq, git and GNU coreutils, nothing else.

  • 10 workflow skills
  • 3 guard hooks
  • 2 install paths: Nix or symlinks

What agent-playbook is, and who it is for

agent-playbook is a set of plain files that tell a coding agent how to work in a repository: how to take an issue to a pull request, how to coordinate several agents, and how to review and publish their work. Other agents read their own skill directories, so the same files can be linked into them.

It is for people who run agents in git repositories and want their rules written down, reviewed and versioned.

Who it is for, by tier

  • A solo or quick repo: Tier 0.
  • An active product repo with parallel agents: Tier 1.
  • Several hosts publishing to a protected branch: Tier 2.

What it is not

  • Not a sandbox. The guards stop a well-meaning agent from drifting. The README and the blueprint both say they are not a defense against a determined adversary.
  • Not a runtime. Nothing in the repository launches an agent or a worker.
  • Not a substitute for a repo's own AGENTS.md. The templates ask each repo to keep only the rules the code cannot show.

What the repository holds

Six top-level parts. Each one has a single job; the blueprint and the README say which file does what.

agent-playbook/

skills/

Ten workflow skills, one SKILL.md each. bootstrap-repo also ships the templates in references/. Markdown only.

hooks/

Bash guards for the coordinator, worker and reviewer roles, a shared guard-lib.sh, playbook-registry.sh, which writes the guard registries and builds review snapshots, and tests/test-hooks.sh.

docs/

universal-blueprint.md, the living architecture, and archive/, the frozen evidence behind it.

.github/

workflows/ci.yml runs the hook tests, shellcheck and a skill lint: regular Markdown files only, closed frontmatter, names match their directories and are unique, named references exist.

Root files

README.md for users, AGENTS.md for working on this repository, CLAUDE.md, which only points to AGENTS.md, and the Apache-2.0 LICENSE.

site/

This overview page: one HTML file, one stylesheet, one small script. Nothing is loaded from another host.

The blueprint has six parts: a global skill baseline, shift-based orchestration, independent review, publishing (Tier 2), host admission and containment, and a lean host configuration switch.

Three tiers, adopted in order

Move to the next tier only when its trigger is real. Each tier keeps everything below it.

  1. Tier 0: solo or quick repo

    Applies to scripts, experiments and configuration repos.

    Turns on: a short AGENTS.md with verifiable commands, a CLAUDE.md that points to it, and repo-scoped stack skills.

  2. Tier 1: active product repo

    Trigger: two or more agents work in parallel, UI changes need browser checks, or a defect escaped review.

    Adds: a shift-based orchestrator, the coordinator, worker and reviewer guards, blind-review, and browser-verify for UI repos.

  3. Tier 2: multi-host publishing

    Trigger: several hosts write code that lands on a protected branch.

    Adds: brokered publishing, so workers hold no push credentials; an owner gate for policy paths; per-host admission control.

Each tier keeps the one before it. The bootstrap-repo skill reads only the templates for the tier it is applying.

One shift runs one milestone slice

An orchestrator is a dispatcher: it splits and routes the work. One thread equals one shift, and a shift covers one milestone slice. It never becomes a forever-thread.

A shift rotates when a trigger fires

  • compactions >= 2
  • dispatches_in_shift >= 40
  • shift_age >= 6h
  • the milestone slice is complete

Rotation drains, cancels and hands off

  1. Freeze. The coordinator runs playbook-registry.sh drain <marker>; its guard then refuses new dispatches, except the successor launch that carries the marker.
  2. Drain for up to 15 minutes, then cancel what is left with the host's cancel tool and bump the shift generation.
  3. Stop after two forced rotations. A rotation that had to cancel children counts once, however many it cancelled. After the second, the shift stops rotating and escalates to the owner. It never starts a third.
  4. Hand off. The successor registers itself, records receipt, attaches its watches, schedules a 20-minute heartbeat and acknowledges, then removes its predecessor's registry entry. Only then does the predecessor stop.

Each wakeup runs one pass, then ends the turn

  1. Verify completions by exact PR, branch and SHA.
  2. Advance PRs: build a review snapshot and send green work to blind-review, route fixes to rebase-and-fix, hand work with approval evidence to publish-pr.
  3. Refill slots with the next ready ticket.
  4. Hygiene: settle finished children; clean up only confirmed merges.
  5. Stop the turn. Children and publish jobs run on their own.

From one issue to a merged PR

Each stage hands over an exact tuple: a PR, a base commit and a head commit. A verdict counts only for the tuple it names.

  1. ticket-implementone issue, one PR, exact SHAs
  2. blind-reviewfresh, read-only, one tuple
  3. publish-prapproval evidence and green CI: exact-SHA fast-forward
  4. safe-cleanupmerged work only

REQUEST_CHANGES from blind-review, or NEEDS_REBASE from publish-pr:

  1. rebase-and-fixclassify the change, push with a lease (Tier 2: hand off to the publisher)
  2. blind-reviewthe review the classification asks for, on the new tuple
  • Publishing never rewrites reviewed commits. publish-pr pushes with a lease on the expected base and confirms the PR is MERGED at the exact head.
  • A moved base is not rebased during publish. The PR goes to rebase-and-fix instead, and the queue keeps moving.

Skills that run work and fix it

Four skills. Each folder holds one SKILL.md; the link opens the file.

orchestrate

Run or take over an orchestrator shift for one milestone slice: split work, dispatch workers and reviewers, merge. No hands-on coding.

Use when starting an orchestrator thread, taking over a rotated shift, or a shift hits a rotation trigger.

ticket-implement

Implement one GitHub issue end to end in an isolated worktree: red-green TDD, foreground gate runs, signed linear commits, an exact-SHA PR.

Use when the task is a single issue number, from pre-flight to pull request.

bootstrap-repo

Set up agent rails in a new or existing repository, tier by tier, and add repo-scoped stack skills.

Use when equipping a repo for agents, adding AGENTS.md or CLAUDE.md, or adding project skills.

rebase-and-fix

Apply review fixes, resolve conflicts, renumber migrations and rebase onto a moved default branch. Then classify the change as FULL_HEAD_RE_REVIEW, MECHANICAL_CARRY_FORWARD or DELTA_RE_REVIEW.

Use when a PR is REQUEST_CHANGES, reports NEEDS_REBASE, or conflicts with a moved base.

Skills that review, verify and keep the repo clean

Six skills, from the reviewer's verdict to the disk.

blind-review

An anti-anchored review of one exact (PR, base, head) tuple, from a fresh read-only context over a snapshot with no .git directory.

Use when a PR is green and needs a verdict, or a re-review must confirm a new head.

council-review

A council of cold, independent reviewers that discusses on a shared temporary board (blind round, then all-to-all replies, then consensus) and converges with evidence, for high-impact decisions.

Use when an architecture, security boundary, policy or proposal change needs it. Not for routine PRs.

browser-verify

Verify a UI change in a real browser against the exact candidate build: routes, console errors, network failures, focus and empty states.

Use when a task changes web UI, layout, routing or client-side API behavior.

publish-pr

Land one approved, green PR on the protected default branch by an exact-SHA compare-and-swap fast-forward. Then confirm it is MERGED and clean up.

Use when a PR is approved and green, or a publish stopped because the default branch moved.

safe-cleanup

Inventory and remove stale worktrees, merged branches and build caches. Sized and confirmed first; unmerged, dirty and live work is never touched.

Use when disk space is low, worktrees pile up, or merged branches need removing.

session-miner

Mine session transcripts, CI failures and review rounds for recurring friction, cluster the root causes and turn each into a mechanical fix.

Use when a milestone or a multi-ticket run is over, or the same failure keeps coming back.

Guard hooks: three roles, three sets of limits

Each guard is a PreToolUse hook. It reads the tool call on stdin, exits 0 to allow it, or exits 2 with a reason to deny it.

What each guard allows and denies
RoleAllowsDeniesActive when
Coordinator Read tools, read-only git and gh, gh issue create and comment, GET-only gh api, the publish broker, playbook-registry.sh except removing itself Repo writes, builds, tests, mutating git, merges by CLI or forge tool, wait loops, new dispatches while draining The thread id (PLAYBOOK_THREAD_ID, else T3CODE_THREAD_ID) is listed in the coordinator registry
Worker Writes inside its own worktree; pushes only to PLAYBOOK_WORKER_BRANCH when it is set Writes outside the worktree; pushes to protected branches (PLAYBOOK_PROTECTED_BRANCHES, default main master develop) PLAYBOOK_WORKER_WORKTREE is set
Reviewer Claude Code's Read, Grep and Glob inside the review snapshot. Codex reviewers use Codex's read-only sandbox instead. Bash, write tools, MCP tools, web access, sub-agents, paths outside the snapshot The thread id is in the review registry and its entry names a snapshot_root
  1. A tool call arrives.
  2. The guard is not active for this thread? Exit 0 at once: allowed, nothing read.
  3. The role's rules check the call.
  4. Allowed: exit 0. Denied: the reason is printed, exit 2.

What a denial looks like

A denial carries its reason back to the agent, which can then act on it. These are the messages the scripts build, with placeholders where a value varies.

coordinator-guard: Edit is blocked for coordinators; delegate file changes to a worker.
worker-guard: Edit may only write inside the worktree (<worktree>); refused: <path>
reviewer-guard: Bash is not allowed for independent reviewers; only Read, Grep and Glob inside the snapshot

The guards stop a well-meaning agent from drifting. They are not a defense against a determined adversary. The hard boundaries are the credential and publishing boundaries of Tier 2. The suite in hooks/tests/test-hooks.sh passes at this commit: 266 checks, 0 failed.

Set it up with Nix, or without

Nix is optional. The skills and templates are Markdown. The hooks need bash 4 or newer, jq, git and GNU coreutils; on macOS install GNU coreutils first, or the BSD realpath makes the guards deny everything.

With Nix and Home Manager

Add the playbook as a non-flake input, pass it to Home Manager, and link every skill:

inputs.agent-playbook = {
  url = "github:Nitestack/agent-playbook";
  flake = false;
};

# A Home Manager module:
{ lib, agent-playbook, ... }:
let skills = lib.filterAttrs (_: t: t == "directory")
  (builtins.readDir "${agent-playbook}/skills");
in {
  home.file = lib.mapAttrs' (name: _:
    lib.nameValuePair ".claude/skills/${name}"
      { source = "${agent-playbook}/skills/${name}"; }) skills;
}

CI keeps skills/ Markdown-only, so this deploys no scripts. Hook commands point at ${agent-playbook}/hooks/.

Without Nix

Symlink the skills into your agent's skill directory. Reruns replace the loop's own links and skip anything else with the same name. Other agents read ~/.codex/skills/ or ~/.agents/skills/.

dest=~/.claude/skills
mkdir -p "$dest"
for s in /path/to/agent-playbook/skills/*/; do
  name=$(basename "$s")
  if [ -e "$dest/$name" ] && [ ! -L "$dest/$name" ]; then
    echo "skip $name"; continue
  fi
  ln -sfn "${s%/}" "$dest/$name"
done

Register the three guards as PreToolUse hooks in ~/.claude/settings.json or ~/.codex/hooks.json; the README has both snippets.

The research archive, R1 to R15

The decisions behind the blueprint came from a fifteen-round council. Two reviewer panels scored each round for developer and agent experience, out of 10. The archive is frozen: grep the section you need, and do not read a file in full.

  1. R1 to R2

    Live audits: the skill catalog, Git 2.56 patch-id, and a publish-script bug audit (P1 to P12).

    End scores, panel A and B, DX/AX: 7.5/7.0 and 7.0/6.5

  2. R3 to R6

    Brokered publishing with no worker push tokens, the policy-path owner gate, and a bundle-based host switch.

    8.5/8.5 and 8.5/7.0

  3. R7 to R9

    A static CI unit, Check Runs provenance, verified OpenSSH 10.6p1 and ast-grep 0.51.2 behavior, an isolated fences job.

    8.9/8.6 and 8.5/7.8

  4. R10 to R14

    Diminishing returns: registration race conditions and multi-pointer crash states.

    9.6/9.6 and 9.3/8.9

  5. R15

    The judge trimmed R10 to R15 over-engineering. The lean plan scored 9.4 DX and 9.3 AX.

    9.6/9.6 and 9.5/9.1

Kept from R1 to R9

  • The orchestrator failure mode and the shift model.
  • Skill pruning from 87 to 28, and supply-chain hygiene for external packs.
  • Credential and host boundaries: no worker push credentials, one serialized publish broker.
  • Verified tooling bugs, such as patch-id --verbatim over --stable.
  • A bundle-based, root-isolated host switch.
  • Reviewer independence means a fresh context, not a second vendor.

Trimmed in R10 to R15

  • Stdin injection into read-only reviewers, and transcript parsing on every read.
  • A distributed crash write-ahead log for the host switch.
  • A local attested CI subsystem, built to work around paused hosted CI minutes.

The archive files

  • Research evidence: nine findings, one section each, with the tool version where one was recorded.
  • Council decisions R1 to R15: the scores, what each round changed, and what was kept and trimmed.
  • Full specification v15: a sanitized snapshot of the complete hardened design, including the optional local-CI fallback. Historical: the blueprint holds the current guidance.
  • Archive index: which claim lives in which section, and which versions were re-run.

Adopt it in a new repo

Start at Tier 0. Copy the templates, fill every blank with the repo's real commands, and keep only the rules the code cannot show. Or ask an agent to run the bootstrap-repo skill.

Tier 0: day zero

cp /path/to/agent-playbook/skills/bootstrap-repo/references/AGENTS.template.md AGENTS.md
  • Fill in the format, lint, test and gate commands in AGENTS.md.
  • CLAUDE.md holds one line: @AGENTS.md.
  • Copy the issue and pull request templates into .github/.
  • Write a fail-closed CI: format, lint and test, locked dependencies, read-only permissions, actions pinned to full SHAs. No template is shipped for it.
  • Keep tests off user data and the user's git config.

Tier 1: parallel agents

  • Add REVIEW.md from its template. Reviewers are fresh and read-only.
  • Add docs/orchestration.md with the Tier 1 sections only.
  • Add an AST or compiler rule only for a failure that has recurred.
  • For a UI repo, run one production-build browser check.

Tier 2: several hosts publish

  • Workers hold no push credentials. They hand their branch and SHAs to one publisher, which does every push under one lock.
  • Policy paths need the owner's signed approval on the exact head.
  • Set host caps: pause heavy jobs when memory or pressure rise above their high thresholds or free disk falls below its floor, and resume once they recover.

Verify every file you add against the repo's own CI before you call the bootstrap done.

Adopt the tiers in order, and move up only when the trigger is real.
